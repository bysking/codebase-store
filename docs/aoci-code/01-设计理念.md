# AOCI-CODE 设计理念解析

> 分析对象：https://github.com/aoci-spec/aoci-code （v0.2.0-rc4，Go 实现，FSL-1.1-MIT）
> 本文只讲**为什么这么设计**。功能细节见 `02-功能模块.md`，数据格式见 `03-数据格式与协议.md`，复刻方案见 `04-bun复刻方案.md`。

---

## 一句话概括

AOCI-CODE 是一个**代码库认知索引服务器**（stdio MCP，固定 9 个工具）。它让模型为每个受管文件/数据表手写一行「这东西是干嘛的、和谁强关联、对外契约是什么、什么不能改坏」，把结果存成 Git 可版本化的纯文本，让 Agent **开工前读一次索引就认识整个系统**，而不是每个任务重新 grep 一遍代码库。

定位不是「查得更准」，而是「**不用查**」。

---

## 一、核心洞察：Agent 的成本结构错了

一般 Agent 处理任务的动作序列：

```
理解需求 → 搜索定位 → 读文件 → 拼上下文 → 改代码 → 验证
```

其中「搜索定位 + 读文件 + 拼上下文」是**纯重复劳动**：换任务、换会话、换 Agent 都要重做一遍。而且做得不完整——50 万行代码里 Agent 永远只看到被关键词命中的 5~10 个文件，它对**系统整体形状**是无知的。

AOCI 的判断是：

| 维度 | 传统 RAG / CodeGraph | AOCI-CODE |
|---|---|---|
| 产出时机 | 提问时临时检索 | 平时维护，提问前已存在 |
| 覆盖范围 | 命中片段（有偏） | 受管范围全覆盖（含负空间） |
| 载体 | 运行时向量库/图库 | 仓库里的纯文本，Git 版本化 |
| 生命周期 | 一次性 | 随代码增量演进 |
| 回答什么 | 「在哪」/「谁调谁」 | 「是什么、为什么存在、什么不能改」 |

所以 AOCI 自称**认知基础设施**（AI-Oriented Cognition Infrastructure）：位于「模型/Agent」与「软件系统」之间的中间层，而不是又一个检索工具。

## 二、四条支柱性设计原则

### 原则 1：模型写语义，程序管治理

源码 Root Manifest 的 `#Global-Invariants` 原文：

```
Index semantics are authored only by the Host model, never generated, prefilled, or judged by AOCI
```

这条边界被贯彻到近乎偏执。程序**允许**做（白名单）：

- 收集确定性证据（文件指纹、行数、Git ignore 权威）
- 识别对象身份、算 hash、检测漂移
- 校验格式 / 字符配额 / 引用命名空间合法性
- 执行治理事务（Plan → Stage → Check → Diff → CAS → Apply）

程序**禁止**做（黑名单）：

- 选择标签
- 生成、预填、摘要、压缩、截断、删除、重排、重写、补全 F/R/A/S
- 「机器先出草稿，模型再润色」——**明确禁止**
- 根据文件名/目录/AST/import/路径**猜**业务语义

**为什么这么严？** 一旦程序能生成语义，语义就会退化。程序生成的内容看起来合理但不可信，而 Agent 无法区分「模型写的」与「模板套出来的」，整个索引的信誉一次性崩塌。宁可慢（20 万行 ≈ 1 小时），也不要有污染。

> 工程启示：这是「**宁可失败关闭，也不要静默降级**」在语义层的体现。同类思想在写入层表现为「无法证明的字节绝不覆盖」。

### 原则 2：索引是地图，不是摘要

索引拆成五层，职责严格不重叠：

```
Root     (aoci.txt)          目录 + 版本入口：声明有哪些分册、项目定位、跨域架构、全局负空间
Meta     (aoci.meta.txt)     图例 + 坐标系：标签字典、FRAS 规则、配额、创作合同
Code     (aoci.code.txt)     分册：代码对象的标记
Database (aoci.database.txt) 分册：数据表的标记（可选）
.aoci/   (config/baseline/…) 地图的治理状态（部分不进 Git）
```

每条标记（Entry）只有四个字段 **FRAS**：

| 字段 | 语义 | 关键约束 |
|---|---|---|
| "F" Function | 一个核心职责命题 | "不是清单"，不能罗列功能 |
| "R" Relations | 修改它时必须一起看什么 | "不是完整依赖图"，只选强关系 |
| "A" API | 外部可依赖的稳定契约 | 不是所有方法/字段/调用方 |
| "S" Non-obvious | 不可推断且删了会出事的信息 | 必须同时通过两个问题 |

S 字段准入是全文最锋利的设计，**两问必须同时为「否」**：

1. 能否从对象名、标签、F、R、A 直接推断？能 → 不许写。
2. 删掉它，会不会导致模型改错代码/数据/生命周期？不会 → 不许写。

于是 S 里长出来的全是这种句子：

> 「原生发布绝不会降级为覆盖式重命名；遇到竞态、不安全类型或无法验证的字节时，必须保留第三方状态并失败关闭」
> 「MySQL 5.7.6+，不支持 MariaDB」
> 「这个 managed block 是模板渲染的，改这里等于改模板，不能手改」

这些是**代码里读不出、删掉会踩坑**的东西。S 字段约占索引信息熵的 60%。

### 原则 3：认知是稀缺资源，必须做预算

索引本身占 context，所以 AOCI 把 token 当一等公民：

- **按重要度分配字符配额**：`#S配额: C9-8≤600 C7-4≤200 C3-1≤50`
- **R/S 按档位设 token 目标与上限**：C9 的 R 目标 90 / 上限 180，C1-4 只有 25/50
- **Whole-Index 三级水位**：target 120K / warning 180K / max 240K token
- **配额权威在二进制里**：`#FRAS-v2-Limits-Authority: machine-contract` —— 项目改自己的 Meta 也放宽不了上限，防止自欺欺人

规模标定：70 万行商业代码 → 索引约 300K token。

### 原则 4：认知必须能证明「确实送到了」

AOCI 最独特、也最容易被忽略的设计。问题是真实存在的：

> Agent 声称「我已读取完整索引」，但它可能只读了前 3 个 chunk，或读了却因上下文压缩丢失。

对抗手段（Overview Attestation 链）：

1. 索引超预算时切成 **Chunk**，带 `next_cursor`，Agent 必须顺链读完
2. 读完必须提交一次 **Attestation**（含 receipt）
3. 服务器可回 **Challenge**（问索引里的事实）
4. `check_only` 是紧凑检查点，**不能替代**完整交付
5. 上下文压缩后（`context_compaction` 事件），必须重新完整 Overview，`probe` 不算
6. 索引装不进上下文 → 返回 `delivery_mode=capacity_stop`，**不循环重试**，任务降级为 source-bound
7. handoff 里禁止保留/摘要索引正文、Header、Entry、Chunk、Challenge —— 只允许留 receipt 身份和「请重载」指令

**设计意图**：把「Agent 假装知道」这个最隐蔽的失败模式变成可检测的状态机。所有 System Cognition 输出都标 `derived=true`，Relations 还标 `authoritative=false` —— 时刻提醒读者这不是事实源。

## 三、次级设计取舍（多由真实故障逼出来）

### 3.1 失败关闭优先于可用性

| 场景 | 行为 |
|---|---|
| 目录段历史根无法安全重定位 | 失败关闭，不猜 |
| Volume 声明路径含 `..`/绝对路径/UNC | 失败关闭 |
| 声明的 Volume 文件缺失或非法 | 整个 CognitionSet 失败关闭 |
| 写入前无法回读证明 | 拒绝整批，指名对象 |
| 目录名尾随空格等不可移植路径 | 拒绝并给唯一出路（重命名目录/移出 index 角色），**永不生成可修复候选** |
| 发现第三方并发修改 | 中断并交人处理 |

### 3.2 写入：CAS + 原子替换 + Baseline 最后落

```
Plan → Stage → Check → Diff → CAS → Apply → Baseline
```

- **跨进程锁**（`internal/fs/lock.go`，含进程身份校验防 PID 复用）
- **CAS** 基于内容 hash，不是时间戳
- **同目录临时文件 + 平台原子替换**（`renameat2` / `exchangedata` / `MoveFileEx` 分平台实现）
- **Baseline 最后写**：先落认知，最后落基线。中途崩溃 = 「认知已改但无基线」→ 进入可证明的 **Recovery**，而不是「看似成功但状态半截」
- **多 Volume 一致性**：Volume Apply + Baseline + Scope 投影必须是**同一个 Cognition Transaction** 的一致结果

### 3.3 Managed Scope：明确「什么不进索引」

| 角色 | 含义 | 有正式 Entry |
|---|---|---|
| `index` | 进入正式认知 | ✅ |
| `observe` | 只观察变化，不写 Entry | ❌（参与漂移检测） |
| `exclude` | 明确负空间，连指纹都不算 | ❌ |

**负空间本身是认知**。AOCI 自己的配置里就有：

> `assets/wecom-group-qr.png` —— 「社群二维码，无系统语义，既不读也不指纹」

这条信息让后续 Agent 不再浪费 token 去理解它。AOCI 自身 44 条 scope 规则里大量是 `observe`（如 `textassets/**` 语言包正文：被 manifest 治理，不必在索引里复制）。

### 3.4 Drift Detection 分七种事实

不是简单的「文件变了」：

| 事实 | 含义 |
|---|---|
| **Missing** | 源码不在了，Entry 还在 |
| **Orphan** | Entry 没有对应受管对象 |
| **Stale** | 源码 hash 变了，Entry 没更新 |
| **Unbaselined** | 受管但从未进基线 |
| 换行变化 | 仅 LF↔CRLF 差异（可容忍） |
| 策展差异 | curation 决策与现状不一致 |
| 授权外源文件 | 空文件 / 二进制 / 超限，被挡在 index 角色之外 |

只有能区分这些，「增量维护」才可能只补真正需要补的几条。

### 3.5 数据库是「证据」而非「连接」

```
显式 database 命令
  → 只读系统目录（不读业务数据）
  → Canonical Schema Evidence（规范化 schema 快照）
  → 人工接受 Evidence Hash（人工批准！）
  → 模型据完整证据创作表级 FRAS
  → Cognition 与 Evidence 绑定 → 受治理 Apply
```

- **凭据只通过环境变量名引用，从不保存**
- 不自动发现凭据、不扫 `.env`、不读 Secret 文件
- 目前仅 Environment Credential Provider（Vault/K8s/AWS SM 留接口不做）
- MySQL ≥ 5.7.6，**不支持 MariaDB**；openGauss 6.0.5 受限支持
- 失败不推进任何状态

### 3.6 本地优先 + 无模型客户端

- 单 CGO-free Go 二进制，无 daemon 常驻（MCP 按需启动）
- 二进制里**没有模型客户端**、没有云端点、不上传源码
- 不要求 Neo4j / 向量库 / 远程图服务
- 唯一会开的连接：用户显式声明的数据库（只取 table schema）+ 本机回环状态页
- 状态页只听 loopback，只答 GET/HEAD，不取锁、不写 Ledger、不改仓库字节

## 四、为什么它「用起来烦」——复杂度来源诚实盘点

你的直觉不是错觉，是架构取向的必然结果。

### 4.1 上手路径长

```
下载/校验签名包 → init --agent X → scan → 【必须重启 Agent】
→ 建索引（20 万行 ≈ 1 小时）→ verify → check → 之后靠 Guide 引导增量维护
```

`init` 写完 MCP 配置后**必须重启 Agent 才生效**，而建索引本身依赖 MCP 工具——所以第一步天然是「做一半停下来」。

### 4.2 命令面与概念面都宽

- CLI 命令组 ≈ 19 个（init / scan / verify / check / status / ui / doctor / capabilities / index / database / cognition / mcp / hook / scope / config / ...）
- MCP 工具固定 9 个
- 需理解的概念：FRAS、Volume、Whole-Index、Managed Scope、Baseline、Ledger、Receipt、CAS、Attestation、Chunk/Cursor、Recovery、Scope Change、Curation、Drift(7 种)、automation.mode、cognition_refresh_threshold...

### 4.3 大量复杂度服务于「非功能需求」

| 复杂度 | 服务目标 | 个人/小团队是否需要 |
|---|---|---|
| CAS + 原子替换 + Recovery | 多进程并发写安全 | ❌ 单人基本不需要 |
| Ledger + Verify History | 审计可追溯 | ❌ 极少用 |
| Attestation/Challenge 链 | 防 Agent 假装读过 | ⚠️ 有价值但可极简 |
| Legacy → Volumes 迁移 | 老版本兼容 | ❌ 新项目完全不需要 |
| Scope Change 正式流程 | 受管范围变更治理 | ⚠️ 简化成改配置文件更实用 |
| 多宿主 Hook（Codex/Claude/Cursor/OpenCode/Qoder/Pi） | 一键接入 | ✅ 但只需 1~2 个 |
| 签名包 + SBOM + cosign + attestation | 供应链安全 | ❌ 自己用不需要 |
| 双 Locale（zh-CN / en-US） | 国际化 | ❌ 中文够用 |
| System Cognition 投影（Lineage/Relations/Impact/Snapshot/Evolution） | 图查询视图 | ⚠️ 可后置 |

**结论**：约 **60~70% 的代码量服务于治理完备性、供应链与兼容性**，而非核心认知价值。核心价值（手写 FRAS + 全量索引读入 + 漂移检测）用 **1500~2500 行 TS** 就能覆盖 80%。

源码规模参考：1820 个文件，其中 `internal/` 下 36 个包，仅 `cli` 52 个文件、`mcptools` 50 个文件、`fs` 31 个文件。

### 4.4 但有些「烦」是必要代价

必须承认：

- **首次建索引必然慢**（模型逐个读文件写条目），这是语义质量换来的
- **模型必须手写 F/R/A/S**，程序代劳就毁了索引信誉
- **S 字段门槛高**，模型常写不够好，需要重写

剩下的「烦」（19 个命令、6 个宿主、签名校验、迁移路径）都是可以砍的。

## 五、设计理念总结（可复用的 8 条）

1. **把重复劳动沉淀成资产**，而不是每次加速它。
2. **语义归模型，机制归程序**，边界写进不变量，且禁止「先机器草稿再润色」。
3. **索引是地图**：图例(Meta) / 坐标(标签) / 标记(Entry) / 目录(Root) / 分册(Volume) 职责不重叠。
4. **S 字段两问准入**：能推断的不写，删了不出事的不写。信息密度靠减法。
5. **认知占 context，所以必须做预算**：按重要度分档配额，且配额权威在二进制里。
6. **失败关闭优于静默降级**：无法证明的字节绝不覆盖，无法安全解析的路径绝不猜。
7. **负空间是认知的一部分**：明确「什么不进索引」与明确「什么进」同等有价值。
8. **认知必须可交付证明**：Chunk + Cursor + Attestation + Receipt，把「假装知道」变成可检测状态。

## 六、一句话回答「值不值得复刻」

**值得，但要砍。**

- **保留**：FRAS 格式、Whole-Index 一次读入、三角色 Managed Scope、漂移检测、模型手写语义的不变量、增量维护的引导闭环。
- **砍掉**：Legacy 迁移、多层事务 CAS 与 Recovery、Ledger、Attestation 挑战链、Scope Change 正式流程、签名供应链、双 Locale、多宿主 Hook、UI 面板、System Cognition 投影。
- **Bun 的收益**：TS 原生 + `bun build --compile` 单二进制 + 内置 SQLite（可存基线）+ 内置测试，能把 1820 文件的 Go 项目压到 **1500~2000 行 TS**，开发迭代快一个量级。

具体方案见 `04-bun复刻方案.md`。
