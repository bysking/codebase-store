# AOCI-CODE 数据格式与协议

> 权威来源：`spec/public/` 下 21 份公开契约。**运行中二进制的 Tool Description、JSON Schema 和机器状态值才是最终权威**，本文是阅读入口。

---

## 一、文件布局

```
<repo>/
├── aoci.txt                    Root：声明 CognitionSet 组成与激活入口
├── aoci.meta.txt               Meta：标签字典、FRAS 规则、配额、创作合同
├── aoci.code.txt               Code Volume：代码对象 Entry
├── aoci.database.txt           Database Volume：表级 Entry（可选，默认不存在）
├── AGENTS.md                   含托管规则块（由 init 渲染，勿手改）
└── .aoci/
    ├── config.json             团队策略、Locale、Scope、预算（进 Git）
    ├── baseline.json           源码/认知/数据库三方绑定的基线（进 Git）
    ├── curation.json           文件级 include/exclude 决策（可选）
    ├── *.draft / ledger.jsonl  草稿、账本、事务、恢复证据（通常不进 Git）
    └── ...
```

宿主配置文件（`.mcp.json` / `.codex/config.toml` / `opencode.json` / `.cursor/mcp.json`）
含**本机绝对路径**，必须加入 `.gitignore` 且不提交——安装器按「条目是否存在」做幂等判断，
提交后的坏路径在其他机器上会被**静默保留**。

## 二、Root 文件格式（`aoci.txt`）

`aoci init` 为 `zh-CN` 项目写出的内容：

```text
#AOCI-ROOT-MANIFEST: 1
#Format-Version: cognition-volumes/v1
#Locale: zh-CN
#Project: my-service
#Global-Invariants: -
#Volume: id=meta kind=meta path=aoci.meta.txt format=meta-v1 depends=- state=enabled
#Volume: id=code kind=code path=aoci.code.txt format=object-fras-v2 depends=meta state=enabled
```

启用 Database Cognition 时追加：

```text
#Volume: id=database kind=database path=aoci.database.txt format=table-fras-v2 depends=meta state=enabled
```

### 关键规则

| 规则 | 说明 |
|---|---|
| 布局判定 | **第一逻辑行必须精确等于 `#AOCI-ROOT-MANIFEST: 1`**（大小写敏感）才走 volumes-v1；没有该标记 → legacy-monolithic；有前缀但不等 → **damaged Root，失败关闭**，绝不退回 Legacy |
| 发现入口 | 只认配置的 `index_path`。**不 glob `aoci.*.txt`，不从磁盘文件推断布局** |
| Volume 声明 | 每个存在的 Volume 精确声明一次。六字段版第 6 位 `state` 可为 `enabled`/`disabled`；五字段版等价于 enabled |
| 路径校验 | 必须是**规范化 repo-relative 路径**。绝对路径 / 盘符 / UNC / `..` / 重复 id / 大小写折叠后重复 → 失败关闭。声明的文件必须是普通文件，不能是符号链接 |
| Meta | 必须 enabled |
| 未声明的固定名文件存在 | 「unmanaged candidate warning」——它的字节和对象都**不算认知** |

四种状态区分：

- **undeclared**：不存在、合法、不创建文件
- **declared 且结构有效**：存在，含只带 marker 的空 Volume（`object_count=0`）
- **declared 但缺失或非法**：`invalid`，整个 CognitionSet 失败关闭
- **固定名文件存在但未声明**：warning，不算认知

### `#Project` 行可以很长

AOCI 自己的 `#Project` 行就是一段完整定位描述。`#Global-Invariants` 里通常写最不可违反的几条（AOCI 自己写了 6 条）。

## 三、Meta 文件格式（`aoci.meta.txt`）

```text
#AOCI-META-VOLUME: 1
#Object-Protocol: repository-cognition-object/v2
#FRAS-Discipline: 2
#FRAS-v2-Limits-Authority: machine-contract
#S-Admission: non-inferable-and-error-preventing
#S quota: C9-8≤600 C7-4≤200 C3-1≤50
#Object-Kinds: code=file database=table
#Canonical-Tag-Authoring: compact A+B+C+[D]+E; dotted form is read compatibility only
#Code canonical identity example: code:path/to/file.go
#Section root: /<repository> stands for the root of the checkout holding this index...
#Code Entry example: file.go[CG7T]: F:Runs the example application | R:- | A:- | S:-
#[Tag dictionary: code]
#A Layer: C-Code
#B Module: G-General
#C Importance: 9-core 8-high-frequency 7-business 5-routine 3-supporting 1-edge
#E Scale: L-large>400 M-medium200-400 S-small100-200 T-tiny<100
#[Tag dictionary: database]
#A Layer: D-Database
...
```

### 三行最吃劲的

| 行 | 含义 |
|---|---|
| `#FRAS-v2-Limits-Authority: machine-contract` | **字段上限归二进制，不归这段文本**。项目改自己的 Meta 也放宽不了上限 |
| `#S-Admission: non-inferable-and-error-preventing` | S 准入原则：不可推断 + 防止错误 |
| `#S quota: C9-8≤600 C7-4≤200 C3-1≤50` | 按重要度分配 S 字符预算 |

### 官方 starter 标签字典（zh-CN 完整版）

```text

         P-持久化 I-集成适配 R-运行基础 L-库与SDK F-声明配置 O-运维交付
         T-测试验证 S-文档规范 X-开发工具 Z-其他
#B Module: G-跨域通用 U-用户交互 B-核心业务 D-数据状态 I-身份权限

          R-可靠性恢复 P-性能资源 W-流程调度 A-分析智能 H-硬件设备
          L-本地化 V-构建发布 Q-质量保障 E-扩展插件 Z-其他
#C Importance: 9-最高 8-很高 7-高 6-较高 5-中等 4-较低 3-低 2-很低 1-最低
#E Scale: L-大>400 M-中200-400 S-小100-200 T-微<100
```

数据库字典的 A 轴不同：

```text
#A Layer: E-实体主表 T-事务事实 R-关联映射 M-明细从属 C-参考字典
```

## 四、Entry 格式（FRAS）

### 4.1 物理结构

Code Volume 只以一行开始：

```text
#AOCI-CODE-VOLUME: 1
```

其后是目录段 + Entry：

```text
===/<repository>/===
.gitattributes[CG3T]: F:Normalizes repository text line endings for deterministic hashes | R:- | A:- | S:autocrlf rewrites would mark the whole tree stale

===/<repository>/internal/fs/===
atomic.go[CG9L]: F:提供持久化替换 CAS、创建 CAS、原子写入和禁止覆盖的恢复移动 | R:code:internal/fs/atomic_exchange_linux.go,code:internal/fs/atomic_exchange_windows.go,code:internal/fs/lock.go | A:AtomicWrite,AtomicWriteCAS,AtomicCreateCAS,AtomicMoveCAS | S:原生发布绝不会降级为覆盖式重命名；遇到竞态、不安全类型或无法验证的字节时，必须保留第三方状态并失败关闭
```

### 4.2 语法

```
<basename>[<tag>]: F:<...> | R:<...> | A:<...> | S:<...>
```

| 部分 | 规则 |
|---|---|
| **目录段头** | `===` + 可选描述 + 以 `/` 结尾的绝对目录 + `===` |
| **Entry 名** | 目录段内的**裸文件名**。读者先按原文读，失败时回退到「紧跟 `: F:` 的括号组是标签，之前全是文件名」（支持 `[...id].jsx`） |
| **分隔符** | `:` 后接空格，字段间 ` \| ` |
| **空字段** | 写 `-` |

### 4.3 目录段的历史根与重定位

`===/.../===` 里的绝对路径是**历史坐标，不是运行时路径**。

- 自 0.2.0 起，writer 新建第一个目录段时写**中性根** `/<repository>`
- 中性根下的目录段按 repo-relative 解析：`===/<repository>/internal/fs/===` → `internal/fs/`
- `<` 和 `>` 在 Windows 是保留字符，所以任何 checkout 都不可能真在那个路径下 → **永远通过重定位解析**
- 克隆/移动仓库**无需重写索引**
- 0.2.0 之前创建的索引保留其记录根，可用 `index relocate` 在一次 receipted 事务里改成中性根
- 历史段无法安全无歧义映射 → **失败关闭**，不猜

> 披露边界：0.2.0 前创建的索引，目录段里可能含主机名/用户名等私有拓扑，**首次公开提交前应人工 review**。

### 4.4 对象身份

| 类型 | 规范身份 | 示例 |
|---|---|---|
| Code | `code:<repo-relative-path>` | `code:internal/fs/atomic.go` |
| Database | `database://<source>/<namespace>/<table>` | `database://primary/public/orders` |

**物理 Volume 决定 object_type**：Code v1 对象是文件，Database v1 对象是表。

### 4.5 FRAS 语义约束（最容易被写坏的地方）

| 字段 | 是 | 不是 |
|---|---|---|
| **F** | 一个核心职责**命题** | 功能清单、能力罗列 |
| **R** | 理解或安全修改它**必须一起看**的强关系集合 | 完整依赖图、所有 import |
| **A** | 稳定的、外部可依赖的访问契约 | 所有方法/字段/调用方/查询/helper |
| **S** | 高熵系统约束认知 | 摘要、synopsis、F/R/A 的重复 |

**R 的写入形式**（新 Volumes Entry 和变更过的 R）：

```text
code:<repo-relative-path>          ← 精确身份
database://<source>/<ns>/<table>   ← 精确身份
-                                   ← 无
```

- 逗号分隔
- **唯一裸文件名或表名不是写别名，绝不静默补全**
- 持久化的裸关系在 R 未变更时保持可读（兼容），但不是创作形式
- 值**永远不是解释性散文**

**S 的两问准入**（每句话都要同时通过）：

1. 能否从对象名、标签、F、R、A 直接推断？→ 能，则不许写
2. 删掉它会不会导致模型改错代码/数据/生命周期？→ 不会，则不许写

补充规则：
- 起始字典里 A 轴和 B 轴都保留 `Z` 表示「已理解但不属于任何命名类别」
- **`Z` 不是证据不足的占位**，字典缺口也不是 S 约束

## 五、标签（Tag）格式

### 5.1 物理形式

```text
compact A+B+C+[D]+E
```

例：`CG9L` = `C`(共享基础) + `G`(跨域通用) + `9`(最高重要度) + `L`(大>400行)，无 D 值。

- 新 Volumes 创作只用 compact 一种物理形式
- **dotted 形态仅用于 Legacy 读兼容**，新创作不产出
- D 是可选维度，**只有当前正式 Meta 声明后才能用**
- 所有消费者通过统一的 `ParseTags` 拆分

### 5.2 E 规模轴

| 值 | 行数 |
|---|---|
| L | > 400 |
| M | 200~400 |
| S | 100~200 |
| T | < 100 |

## 六、MCP 协议契约

### 6.1 传输与身份

| 项 | 值 |
|---|---|
| 传输 | stdio |
| `serverInfo.name` | `aoci-code` |
| `serverInfo.version` | 注入二进制（如 `0.2.0-rc4`） |
| **stdout** | **只用于 JSON-RPC 帧** |
| stderr | 日志与诊断 |
| 单帧上限 | **16 MiB** |
| `tools/list` 缓存提示 | `ttlMs: 0`, `cacheScope: public`（让 Host 每次重取） |
| 未知方法 | `-32601` |

协议版本协商（**新→旧**）：

```
2026-07-28  ← 当前身份，无会话修订
2025-11-25
2025-06-18
2025-03-26
2024-11-05
```

- `initialize` 握手最多答到 `2025-11-25`
- 无会话修订（`2026-07-28`）的客户端在每个请求的 `_meta` 里带 revision、client info、capabilities，且可以从 `server/discover` 开始
- 其它修订的**无会话请求** → JSON-RPC 错误 `-32022`，data 里列出支持的版本

### 6.2 九个工具

```
aoci_get_entries    aoci_header    aoci_maintain
aoci_overview       aoci_remove_entry
aoci_report         aoci_rules     aoci_search
aoci_update_entry
```

工具名排序后以 LF 连接（末尾也加 LF）的 SHA-256：

```
b4a56cb6d4e625189708e2132a45094eecc62a05c6a1bd4d06ddd0471598176e
```

**九工具身份独立于可选 CLI 生命周期命令**：改 CLI 命令不会隐式增删改名 MCP 工具。

### 6.3 Schema 说明

- 运行中服务器的 tool description + input schema **就是机器契约**
- 每次调用按该工具注册的 closed schema 校验
- `tools/list` 展示 schema，**但有两个 `aoci_overview` 成员例外**：`cognition_receipt`（回传上一次返回的 receipt）和 `probe_answers`（回答刚才 `check_only` 发出的探针）——它们在 list 里只显示为 plain object，但校验时仍保持 closed shape
- description 只说「做什么、何时调、可能写什么」，**procedure 在 `aoci_rules` 会话合同、Guide 和响应自身字段里**，description 不重复

### 6.4 配置读取行为

Server **启动时读配置、每次调用也读，但永不写**。

无配置的 Legacy 索引，或配置早于 Locale 字段 → 以 `zh-CN` 服务，**但不记录该 Locale**（普通 CLI 命令会记录）。

## 七、Overview 交付契约

### 7.1 正文结构

每次完整 Overview 的正文 = **起始标记 + 当前正式索引的精确内容 + 结束标记**。

### 7.2 分块规则

超预算时：

1. 立即从 **Chunk 1** 开始
2. Agent **必须**沿 `next_cursor` 读到最后一个 Chunk
3. 读完用已交付的 Whole-Index 提交一次 **Attestation**
4. **不得**用局部搜索、旧记忆、源码补读或直接读文件冒充完整交付
5. Pending Recovery 或不一致快照 → **失败关闭**，不混合内容

### 7.3 参数

| 参数 | 值 |
|---|---|
| `overview_delivery.chunk_tokens` | 唯一交付大小设置，**默认 7000**，有效 **4000~24000** |
| `check_only=true` | 不含 Chunk 链的紧凑检查点（**不能替代**完整交付） |
| `cognition_refresh_threshold` | 默认 30 条不同语义路径 |

### 7.4 结果大小上限声明

`aoci_overview` 单工具声明了结果大小上限。有些宿主会把过大工具结果**落盘**、只把预览放进上下文——那对认知交付等于**静默失败**。这个声明让它们只为这一个工具抬高阈值。

Claude Code 上 `24000` 可放心用，480 个对象的索引由 5 块变 3 块。这是**静态声明，不做宿主探测**；不认识的宿主按 MCP 规范忽略。

### 7.5 上下文压缩后的恢复协议

已知发生压缩后：

1. Rules 无法可靠保留 → 先重读 `aoci_rules`
2. 用新事件 ID 声明 `context_compaction`
3. 完成一次**普通完整** Overview 的 cursor → 确认 → Attestation 序列
4. `check_only` 和认知 `probe` **不能替代**
5. 完成新完整传输后，**即使 Attestation 是 partial 或 fail**，也继续按既有规则执行 source-bound 任务，**不再自动调第二次 Overview**
6. 索引装不进上下文 → 一次重载本身被压缩打断后，服务器对下一次重载答 `delivery_mode=capacity_stop`，任务按 source-bound 继续

**handoff 允许保留的**：receipt 身份、未完成 write 或 Recovery 状态、立即重载指令。
**handoff 禁止保留**：Whole-Index 正文、Overview Header、Entry、Chunk、Challenge、Attestation 正文（及其摘要）。

> 复制进 handoff 的索引语义或 receipt **不能证明当前模型认知可靠**。

## 八、状态与发现值

### 8.1 next_action 枚举

```
authoring_required      → 需要模型创作 Entry（附批次 + 创作合同）
evidence_required       → 需要数据库 Evidence
review_observed         → 有 observe 变更待复核（附 observe_review）
scope_change_required   → 受管范围需走正式改变流程
cognition_budget_exceeded → 超出认知预算
none                    → 无事可做（可能附 terminal_proof）
```

### 8.2 对齐状态

```
aligned / authoring_required / evidence_required / observed_pending /
scope_change_required / cognition_budget_exceeded / stopped
```

`exit_code=0` **仅当**所有启用 domain 都 aligned 且无 scope/observe/budget 阻塞。

### 8.3 漂移事实

```
Missing / Orphan / Stale / Unbaselined / 换行变化 / 策展差异 / 授权外源文件
```

### 8.4 Repair Finding schema

所有候选校验失败共享**一个** machine-facing Repair Finding schema：

- 每个生产批次候选带不可变的 original position
- 完整批次里**所有**可独立修复的候选错误都在
- 当前 Meta 有效但候选标签语法非法 → 特定修复路径
- 目录名不可移植这类**不可修复**的，答 stop + 唯一出路，**永不生成可修复候选**

### 8.5 Terminal Proof

最后一批 Apply 到达 aligned 时携带：

```json
{ "terminal_proof": { "format": "terminal-proof/v1", ... } }
```

同一组值还会出现在 `root_overview_result` 里。**`terminal_proof` 之后才算真正收工**；单次 acknowledgement 既不能创建 Entry 也不进入 alignment / terminal_proof / 任何身份。

## 九、数据库证据契约

### 9.1 链路

```
显式 database 命令
  → 只读 PostgreSQL/MySQL/openGauss 系统目录
  → Canonical Schema Evidence
  → 人工接受 Evidence Hash
  → 宿主模型根据完整证据创作表级 FRAS
  → Cognition 与 Evidence 绑定后进入受治理 Apply
```

### 9.2 Canonical Schema Evidence

- 内容**确定性规范化**（同 schema 得同 hash，跨库/跨版本可比）
- 只采**系统目录元数据**，不读业务数据
- 失败**不推进任何状态**

### 9.3 凭据边界

| 允许 | 禁止 |
|---|---|
| 通过**环境变量名**引用 | 保存凭据值 |
| 显式声明数据源 | 自动发现凭据 |
| 只读 Schema 元数据 | 扫 `.env` |
| | 读 Secret 文件 |
| | 绕过数据库管理员权限边界 |

当前只提供 **Environment Credential Provider**。Vault / K8s Secret / AWS·GCP·Azure Cloud Secret Manager 可以后续通过同一 Provider 边界接入，**但当前不可用**。

### 9.4 支持矩阵

| 数据库 | 版本 | 备注 |
|---|---|---|
| PostgreSQL | 通用 | 纯 Go 驱动 |
| MySQL | **≥ 5.7.6** | **不支持 MariaDB**；校验 CHECK / index expr / visibility |
| openGauss | 6.0.5 | **受限支持**，A/PG 兼容模式，verify-full；带本地 replace 的补丁驱动 |
| SQLite | 文件型 | 可能触及 `-shm` |

## 十、System Cognition 派生契约（全部 `derived=true`）

| 能力 | 数据来源 | 持久化新事实 | 边界 |
|---|---|---|---|
| **Lineage** | Cognition / Evidence / Receipt / Baseline 绑定 | 否 | 解释来源链，**不成为独立 Provenance 数据库** |
| **Relations** | Root Manifest + Volumes + 正式 Entry 的规范 R | 否 | `authoritative=false`；**不从 SQL / import / 路径 / 名称猜关系** |
| **Impact** | 当前正式 R 关系及可解析身份 | 否 | 不自动推断业务语义 |
| **Snapshot** | 当前权威资产的确定性观察 | 否 | 输出**由调用方保存**，不是 Baseline 或 Recovery 资产 |
| **Evolution** | 调用方提供的旧 Snapshot vs 当前投影 | 否 | 比较观察，不推进独立生命周期 |

**未解析的 R 关系形成不完整结果或诊断，而不是由程序猜测补全。**

> **AOCI-CODE 不是知识图谱系统。** Relations 可看作便于查询的关系视图，但它**不拥有第二套状态管理、独立写入路径或新的事实存储**。删除派生输出可从权威资产重算；冲突时以权威资产为准。

## 十一、宿主集成矩阵

| 宿主 | 接入方式 | 边界 |
|---|---|---|
| **Codex** | 项目级 stdio MCP；可选 `--hooks`（压缩 prompt + `SessionStart(compact)`） | 必须过 Codex `/hooks` 审查并信任；**不装**编辑 Hook |

## 十二、只读命令的真实边界

`verify` / `check` / `index score` / `index inventory` 的「只读」**仅表示不修改正式索引或 Baseline**，不等同于零文件写入：

- Ledger 启用时四者都可能**追加本地 Ledger**
- `verify` 还会尝试写 **Verify History**
- **审计写入失败不改变既有退出码与治理判据**

需要零文件写入时：**用隔离副本**。当前公开 CLI **没有**一次性关闭所有 Ledger 与 Verify History 写入的总开关。

## 十三、写入安全契约

```
Plan → Stage → Check → Diff → CAS → Apply → Baseline(最后)
```

| 机制 | 实现 |
|---|---|
| 跨进程锁 | `internal/fs/lock.go` + 进程身份校验（防 PID 复用） |
| CAS | 基于内容 hash，非时间戳 |
| 原子替换 | 同目录临时文件 + 平台原语（`renameat2(RENAME_EXCHANGE)` / `renamex_np(RENAME_SWAP)` / `ReplaceFile`） |
| 回读证明 | 写入前证明每条 Entry 能从将要发布的 Volume 读回；有一条不成立 → **拒绝整批并指名对象** |
| Baseline 最后落 | 崩溃 = 「认知已改但无基线」→ 可证明 Recovery，而非半完成状态 |
| 多 Volume 一致性 | Volume Apply + Baseline + Scope 投影 = 同一个 Cognition Transaction 的一致结果 |

### 幂等与重放

- 批次的 `original position` 不可变
- `cognitionplan/replay.go` 支持重放
- `tools_write_batch_recovery.go` 处理中断批次的恢复
- 第三方并发修改 → 中断并交人处理（`transaction_guard.go`）
